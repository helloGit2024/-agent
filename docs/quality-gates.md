# 质量门禁

> 门禁与纪律的唯一区别：**门禁有「不通过时的动作」，且那个动作是「停」**。
> 本项目的门禁分两层：**机器门禁**（`make gate`，每次提交跑）与**人工门禁**（阶段出口，跑不了就停）。

## 1. 机器门禁（`make gate`）

`ci/gate_all.py` 当前 6 组（S0.9 加了 D 组），S5 后 8 组。**新增门禁必须进 `GATES` 列表**（P-12）。

| 组 | 内容 | 通过标准 | 现状 |
|---|---|---|---|

| B 壳 | `selftest_v2.py` | 84/84（S0.5 是 77，S0.9 +7） | ✅ |

| D 回归 | `eval/regress_demo.py` 7 题字节级 | 7/7 一致 | ✅ |
| E 静态 | `ci/check_imports.py` 门禁 1/2（S2 加门禁 3） | 0 违规 | ✅ |
| F 语义一致性 | `ci/check_semantic.py`：9 指标 + 四态分流 + 配置生效 + 11 工具面 + 分源签名 + 升格下线 + 出口闸门认 ref_id | 11 条全绿 | ✅ |

**失败处理**：
- A/B/C/D 红 → **停下改代码**，不许改断言（P-11）。
- F 红 → 说明两处实现已经不自洽（例：指标注册了但没进 enum），**先对齐再继续**，不许靠改其中一边通过。
- E 红 → 停下改 import，不许把文件加进白名单（白名单只允许 V1 历史文件）。
- G/H 红 → 先判断是「实现错」还是「设计变更」，设计变更走 ADR + 重录基线。

## 3. 每个任务的「完成定义」（DoD）

一个任务只有同时满足下面 5 条才算完成：

1. **功能**：`spec.md` 对应 FR 的验收方式跑通（贴命令与输出）。
2. **回归**：`make gate` 全绿；未重录任何基线（除非按 P-11）。
3. **断言**：新增 ≥1 正向 + ≥1 反向断言，且断言名能当文档读（描述「为什么」不是「是什么」）。
4. **文档**：`tasks.md` 状态回填；若改了表/接口/schema，同步 `data-model.md` / `api-contract.md`。
5. **可解释失败**：新增路径的失败都有 9 个错误码之一 + `detail`，无裸异常。

## 4. 提交前 60 秒自检（贴在显示器上）

```bash
make gate                  # 必须全绿
git status                 # 只改 tasks.md 落点内的文件
git diff --stat            # 单次改动 ≤ 400 行（超了拆任务）
grep -rn "TODO\|FIXME" <改动文件>   # 新 TODO 必须在 tasks.md 有落点
```

## 5. 不许做的四件事（门禁管不到，但后果一样重）

| 行为 | 为什么不行 | 正确做法 |
|---|---|---|
| 为了让测试绿而改 expected / 删断言 | 等于改答案（P-11） | 判断是代码错还是设计变；设计变走 ADR + 重录说明 |
| 在渲染层写业务特判（`if product == ...`） | 绕过册子 = 第二套口径（T-09） | 改册子或加参数 |
| 把 `bins` 的切点做成可传参数 | 单调性可被任意塑形（§8.4） | 只收箱数，切点由函数生成 |
| 把明细「先查出来再脱敏」 | 越权已发生（P-03） | 在 `select_*` 就注入 `row_filter` |
